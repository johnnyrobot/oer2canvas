# Canvas embedded-image probe validation — 2026-08-28

Evidence for document-import issue 07. Produced by `npm run probe:canvas-images:run` against a
live Canvas instance; the machine-readable observations are
[`canvas-image-probes-2026-08-28.json`](canvas-image-probes-2026-08-28.json).

## Result

`standalone-webcontent` is the shape production may implement. `webcontent-dependencies` passed
every required behavior too; the recommendation breaks the tie toward the simpler manifest.

`page-owned-files` and `associatedcontent-dependencies` **failed outright**: Canvas reported the
import as `completed`, then attached no course files at all.

## What production must do

- **Declare each asset as a standalone `<resource type="webcontent">`** whose `href` and `<file>`
  both point at the packaged path. Page-owned `<file>` children and `associatedcontent` do not work.
- **Page `<dependency>` elements are optional.** They neither helped nor hurt: the two shapes that
  differ only by dependency declarations behaved identically on every measured dimension.
- **Emit the reference `$IMS-CC-FILEBASE$/<path relative to `web_resources/`>`.** Canvas accepted the
  archive-root form the probes packaged (`$IMS-CC-FILEBASE$/web_resources/probe/x.png`) but its own
  export emits the `web_resources`-relative form (`$IMS-CC-FILEBASE$/probe/x.png`). Both import, so
  the round trip survives either way; production should emit the form Canvas itself emits.
- **Do not assume the packaged path is the Canvas Files path.** `web_resources/probe/single.png`
  lands at `course files/probe/single.png`; Canvas strips the `web_resources/` prefix.
- **Do not rely on deduplication.** Two files with byte-identical PNG content stayed two distinct
  Canvas Files. Production must not assume Canvas collapses duplicates.
- **A shared image is safe.** One packaged asset referenced by two pages resolved to a single Canvas
  File from both, and stayed single through a course copy.

## Canvas rewriting observed

Canvas rewrites the packaged reference on import to an absolute course-file URL and adds attributes
the cartridge never contained:

```html
<img src="https://<canvas>/courses/<id>/files/<fileId>/preview" alt="…" width="16" height="16"
     loading="lazy" data-api-endpoint="https://<canvas>/api/v1/courses/<id>/files/<fileId>"
     data-api-returntype="File">
```

Alt text, `width`, and `height` survived unchanged on every passing surface. The added
`loading="lazy"` is why the harness forces eager loading before measuring: a lazily deferred image
below the fold is indistinguishable from a broken one by natural size alone.

For the two failing shapes the reference was left unresolved as
`/courses/<id>/file_contents/course%20files/web_resources/probe/single.png`, accompanied by four
`Missing links found in imported content - Wiki Page body` warnings. Re-exporting such a course
produced a corrupt hybrid that is neither a token nor a working URL, with no image entries at all:

```html
<img src="http://<canvas>/courses/<id>/file_contents/$IMS-CC-FILEBASE$/web_resources/probe/single.png" …>
```

Note the downgrade to `http://`. A course imported through a failing shape does not merely render
broken images; its own Canvas export is unusable.

## Round trip

Exporting a course imported through the winning shape produced a valid cartridge whose manifest uses
standalone `webcontent` resources and `$IMS-CC-FILEBASE$/probe/<filename>` references. Re-importing
that export into a clean course preserved all four pages, all seven assets, every raster type, and
all alt text.

## Redaction

The Canvas hostname and operator name are replaced with `canvas.example.edu` and `redacted` in this

## Limitations

- **One Canvas environment.** All observations come from a single self-hosted instance
  (Chromium 151.0.7922.34). No second environment or release was available, so nothing here is
  evidence of cross-version behavior.
- **Small synthetic rasters.** Fixtures are 16×16. Nothing here bounds Canvas's behavior on large
  images, animated GIFs, or files near an upload limit.
- **`todo`-severity migration issues were never produced**, so the harness's handling of them is
  tested but not field-observed.
