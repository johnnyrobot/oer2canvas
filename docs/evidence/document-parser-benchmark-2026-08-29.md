# Browser parser benchmark — 2026-08-29

## Result

Re-run of the 2026-08-27 matrix after PDF import went from a probe to a shipped format. AnyDoc 0.2.4
and PDF Inspector 1.17.0 ran as disposable module Workers in the production Vite build, source
`ArrayBuffer` ownership was transferred to each Worker, cancellation terminated the active Worker
promptly in both supported desktop profiles, and the next parse succeeded in a fresh Worker.

The complete machine-readable report is
[`document-parser-benchmark-2026-08-29.json`](document-parser-benchmark-2026-08-29.json).
Fixtures are deterministic and generated by `scripts/document-parser-fixtures.mjs`; no fixture or
measurement was uploaded.

## What changed since 2026-08-27

**The PDF parse is now two module passes.** `detectPdf` classifies the document, the runner checks
the page budget against that classification, and only then is `processPdf` asked to extract. This is
what lets a 300-page document be refused having built Markdown for none of it, instead of after
building it for all of it. The cost of the second pass is the point of this re-run — see below.

**The recorded result is a measurement summary, not the parse result.** `ParserProbeResult` now
carries content as well as measurements: `normalized.packagedAssets[].bytes` (added by issues 08 and
09) and the PDF `markdown`. Recording them verbatim produced a **486 MB** report, 58 MB of it for
the 64-asset EPUB fixture alone, none of which is a measurement. Sizes and counts are kept and bytes
are not, so this report stays comparable in shape to the 2026-08-27 one.

## The classification pass, measured

The two-phase design was justified on a Node measurement (9.8 ms against 106.6 ms). That claim now
has browser evidence of the same kind every other budget has. On the 200-page fixture:

| Profile | `detectMs` | `parseMs` (both phases) | Classification share |
| --- | --- | --- | --- |
| Chrome desktop | 19.6 ms | 178.1 ms | 11% |
| Firefox desktop | 73 ms | 912 ms | 8% |
| WebKit (diagnostic) | 24 ms | 194 ms | 12% |

Parsing the PDF structure twice costs roughly a tenth of the parse, in every engine, which is what
the design predicted. `parseMs` counts both phases of module work and excludes the message round
trip between them, during which the Worker is idle.

## The gap-attribution pass

A page that produces no text emits no page marker, and `pagesNeedingOcr` does not reliably name it —
measured 2026-08-29, the module only populates that list once the scanned fraction is high enough
for the document to classify as `Mixed`. Each un-marked page is therefore re-parsed alone to
establish whether it is blank paper or an image of text.

`attributionMs` was **0.0–0.4 ms** across every profile and fixture, and `unmarkedPageCount` was
**0** for all three PDF fixtures: they are wholly text-bearing, so no page needed attributing. That
is the normal case, and it does no extra work. The cost is bounded by a budget already enforced
before extraction — `maximumPdfPages` is 200, and each re-parse covers one page.

## Budgets

Unchanged. The slowest successful parse was again `rtf-stress-16m` in Firefox — **4,229 ms** against
4,287 ms on 2026-08-27, well inside the 30,000 ms timeout — and the largest WASM allocation was again
**97,845,248 bytes** against the 128 MiB ceiling, identical to the previous run.
